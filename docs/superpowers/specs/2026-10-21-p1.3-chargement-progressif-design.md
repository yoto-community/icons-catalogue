# P1.3 — Chargement progressif du catalogue par shards (design)

Date : 2026-10-21
Statut : validé (design) — en attente de relecture de la spec

## Contexte & problème

Le front charge aujourd'hui **tout `icons.json` (18,7 Mo)** avant d'afficher la
moindre icône : `IconsDataContext` fait un unique `fetch(INDEX_URL)` puis
construit l'index Lunr (~1,5 s, Web Worker) sur l'ensemble du catalogue.

Or `build:api` produit déjà, dans `dist/`, des **shards par source** et
`index.json` (manifeste), mais ils ne sont pas publiés. Le premier affichage
attend donc la fin du plus gros transfert.

Contraintes produit : le **tri** (défaut : `downloads`) et la **recherche**
sont globaux côté client ; toute vue partielle ne peut pas garantir un tri
global exact avant d'avoir tout chargé.

## Objectif

Réduire le **temps d'affichage** (afficher des icônes avant la fin du
téléchargement complet), à **total téléchargé ~inchangé**, la recherche et le
tri globaux restant disponibles une fois tout chargé.

## Décisions

1. **Mécanisme A** — shards **par source**, fusion progressive, index Lunr
   construit **une seule fois** quand tout est chargé.
2. **`icons.json` retiré de la publication** : l'app et les consommateurs
   passent à `index.json` + shards par source. (Économise ~18,7 Mo déployés en
   double des shards.)
3. **Indicateur de chargement d'arrière-plan** affiché tant que tout n'est pas
   chargé.

## API publiée (après P1.3)

Publiés sur GitHub Pages (`site/public/` → `dist/`) :

| Endpoint | Rôle |
|----------|------|
| `GET /icons-catalogue/summary.json` | Statistiques (inchangé) |
| `GET /icons-catalogue/index.json` | **Manifeste** : sources, compteurs, `catalogVersion` |
| `GET /icons-catalogue/icons-by-source/{source}.json` | **Shards** : `yotopixels`, `yotoicons`, `yoto-official` |

**Retiré de la publication** : `icons.json` (remplacé par le manifeste + les
shards ; `dist/icons.json` reste un artefact **local**). `lunr-index.bin` était
déjà retiré (P1.3 précédent).

> Le manifeste publié (`index.json`) décrit l'**ensemble** du build `dist/`
> (shards par catégorie, `icons/{id}.json`, `search-index.json`…), mais seules
> les entrées `sources` sont réellement publiées. Le front ne lit que
> `sources` ; la documentation le précise.

## Build (racine)

- `scripts/build-api.js` : copier vers `site/public/` → `index.json` +
  `icons-by-source/*.json` (+ `summary.json`). **Ne plus** copier `icons.json` ;
  **supprimer** tout résidu `site/public/icons.json` et
  `site/public/lunr-index.bin` (sinon Vite les redéploierait depuis `public/`).
  Mettre à jour `test-index.html` (endpoints publiés) et les logs.
- `site/scripts/check-data.mjs` : `REQUIRED = ['public/summary.json',
  'public/index.json']` (retirer `icons.json`).
- `.gitignore` : ajouter `site/public/index.json` et
  `site/public/icons-by-source/` (artefacts générés) → le workflow hebdo ne
  commite toujours que `summary.json`.
- **PWA** : aucune modification (la règle runtime `/…\.(json|bin)$/` couvre
  `index.json` et les shards ; `globPatterns` ne précache aucun JSON).

## Front — couche données

- `src/constants/index.ts` : `MANIFEST_URL = ${CATALOGUE_BASE}/index.json` ;
  `sourceShardUrl(source) = ${CATALOGUE_BASE}/icons-by-source/${source}.json`.
- `src/api/` : types `CatalogueManifest` / `ManifestSource`, garde de forme du
  manifeste, `apiClient.getManifest()` et `apiClient.getSourceShard(source)`
  (fetch + `assertIconArray`), plus un helper **pur** `planSourceOrder(sources)`
  (tri par effectif **croissant**, départage par `id`).
- `src/context/IconsDataContext.tsx` :
  - charge `index.json`, puis les shards dans l'ordre de `planSourceOrder`,
    **fusionne** au fur et à mesure (`setIcons(prev => [...prev, ...shard])`) ;
  - `isLoading` = vrai **tant qu'aucune icône** (ou erreur) ; passe à faux **dès
    le 1ᵉʳ shard** → la grille s'affiche sans attendre le reste ;
  - nouveau champ **`isComplete`** = tous les shards chargés ;
  - `searchEngine` construit **une seule fois** quand `isComplete` (évite la
    reconstruction à chaque fusion) ; `isSearchReady` inchangé ;
  - `reload` réinitialise (`icons = []`, `isComplete = false`) puis relance ;
  - **pas de repli `icons.json`** (retiré) : échec du manifeste → `error`.
- `summary.json` : chargement inchangé (non bloquant).

## Front — UI

- `CataloguePage`, `CategoryIconsPage`, `AuthorIconsPage` : gardent le
  `LoadingState` tant que `isLoading`, puis rendent la grille (partielle, puis
  complétée). Pas de nouvel écran.
- **Indicateur** discret tant que `!isComplete` : « Chargement du reste du
  catalogue… » (clé i18n `catalogue.loadingMore`, fr/en) dans la zone de
  résultats (`aria-live="polite"` déjà présent).
- **Échec d'un shard en cours** : conserver les icônes déjà chargées, remplacer
  l'indicateur par un message d'erreur + bouton **Réessayer** (appelle `reload`).
